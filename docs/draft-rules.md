# 記事下書き（drafts）執筆ルール

`drafts/` 配下で記事や実績紹介の下書き（Markdown）を作成・編集する際のガイドラインです。
記事の執筆・推敲時には、文章作成スキル **`natural-japanese`** を必ず適用し、AI臭さのない自然で読みやすい文章を作成してください。

---

## 1. 装飾・記法の禁止事項

### 太字（Bold）の禁止
記事本文・リスト・テーブル内を問わず、**太字記法（`**...**`、`__...__`、`<strong>`、`<b>`）は使用しないでください**。

### 水平線（`---` / `<hr>`）の禁止
セクションの区切りに水平線（`---`）を挿入しないでください（先頭の frontmatter 囲みを除く）。
セクション間の区切りは、見出し（`h2`, `h3`）自体の余白とスタイルによって自然に表現されます。

### 具体的な実装コードの掲載禁止
CSSやスクリプトなどの**具体的な実装コードブロックは掲載しないでください**。
ポートフォリオ記事の役割はコードの断片を提示することではなく、制作の背景や目的、直面した課題への工夫、ユーザー目線での価値を伝えることです。コードを確認したい読者には `codeLink`（GitHub等）を提供します。

### コードブロック内での非コード記述の禁止
フロー図、アスキーアート、矢印付きテキストなどの非コードをコードブロック内に記述しないでください。
処理手順や画面遷移フローを表現する場合は、順序付きリスト（`1.`, `2.`, `3.`）や箇条書きリスト、または通常の文章によって表現します。

### 禁止の背景・理由
- **視覚的ノイズの低減**: ページ内に過度な線や太字、長大なコードブロックが点在すると視線が散り、可読性や落ち着いたトーンが損なわれます。
- **構造化による表現の促進**: 装飾記号に頼るのではなく、見出しやリスト、適切な段落分けといった文章構造によって自然に要点を伝える執筆を徹底します。

---

## 2. 執筆方針：非エンジニアへの伝わりやすさの徹底

採用担当者やデザイナー、ディレクターなど**非エンジニアの閲覧者にも直感的に理解できる言葉遣い・表現**を徹底してください。

1. **専門用語やプロパティ名の羅列を避ける**
   - 難解なCSSプロパティ名（`clip-path: polygon(...)` や `background-blend-mode` など）をそのまま並べるのではなく、「複数枚の画像を重ねて奥行きを出す」「斜めのカッティングで次セクションへ視線を誘導する」のように、視覚的な効果や意図を平易な言葉で説明します。
2. **「何を作ったのか」「どんな工夫をしたのか」に焦点を当てる**
   - 技術の難しさではなく、「なぜその演出が必要だったのか」「ユーザーにとってどんな使い心地・メリットがあるのか」を中心に言語化します。
   - **注意**: 「工夫した点・得られた知見」といった独立したセクションは作成せず、それぞれの工夫や知見は関連する「主な機能」などのセクション内に統合して説明してください。
3. **カギ括弧（「」）やインラインコードの適切な活用**
   - 特定の機能名やキーワードはカギ括弧（「」）等で整理し、専門用語に依存しすぎないようにします。
4. **簡潔で明瞭な文構造**
   - 1文を短く保ち、要点がダイレクトに伝わる推敲を行います。

---

## 3. 文章品質と推敲：`natural-japanese` スキルの適用

記事の新規作成および推敲・リライトを行う際は、文章作成スキル **`natural-japanese`** を必ず適用してください。

### 目的
AI特有の不自然な言い回し（単調な語尾の連続、結論の先延ばし、過度な並列、機械翻訳調の構文など）を排除し、自然でリズムのある日本語文章に仕上げるため。

### 執筆・推敲時のルール
1. **生成時制約と設計**:
   - 読者（非エンジニアの閲覧者）と主メッセージを明確にし、結論・要点から簡潔に記述します。
   - 「〜することができる」「〜と言えるでしょう」といった陳腐な定型句や受動態を避けます。
2. **スキルの手順に沿った推敲・検査**:
   - 記事作成時は `natural-japanese` スキルのガイドラインに従って推敲を行います。
   - 必要に応じて同梱の lint スクリプト（`python3 ~/.agents/skills/natural-japanese/scripts/lint.py drafts/<対象ファイル>.md`）を実行し、AI臭さや読解負荷（一文長、連続漢字など）を客観的にチェックして解消します。

## 4. 技術スタックの記載ルール

実績紹介における「技術スタック」セクションは、**必ず記事の最後に配置**してください。また、以下の 5 つの区分を用いて**採用技術のみをシンプルに列挙**します。

### 5 つの区分
1. **言語**
2. **フレームワーク**
3. **OS**
4. **インフラ**
5. **その他**

### 記述形式のルール
- カテゴリ名や選定理由の解説文は記載せず、採用技術名のみをカンマ区切り等で列挙します。
- Tailwind CSS や shadcn/ui などの CSS / UI ライブラリも「フレームワーク」区分に含めます。
- 該当する技術がない区分は省略します。
- 箇条書きリスト形式で記述します。

```markdown
## 技術スタック

- 言語: TypeScript, Python
- フレームワーク: Next.js (App Router), Tailwind CSS, shadcn/ui
- OS: macOS
- インフラ: Vercel
```

## 5. 基本テンプレート（Frontmatter）

下書きは以下の frontmatter を持つ Markdown 形式で管理します。

```markdown
---
title: "タイトル"
description: "概要説明文"
date: "YYYY-MM-DD"
tags: ["タグ1", "タグ2"]
demoLink: "https://example.com" # 任意
codeLink: "https://github.com/..." # 任意
---

## 概要

本文...

## 開発の背景と目的

本文...

## 主な機能

- 機能1: 説明（ここに工夫した点なども含める）...
- 機能2: 説明...

## 技術スタック

- 言語: TypeScript
- フレームワーク: Next.js, Tailwind CSS
- OS: macOS
- インフラ: Vercel
```
